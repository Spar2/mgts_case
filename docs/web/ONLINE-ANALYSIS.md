# Расчёт реального поля прямо из сайта

13 октября 2026. Рабочий путь: реальное окно → CPU-расчёт → обработка/фон/Z-score → связанное исследование → неизменяемый кейс и ZIP.

## Участнику и Захару

В `/research` откройте «Очистка и анализ участка». Задайте четыре исходных индекса расчёта: начало включено, конец исключён. По умолчанию до 60 профилей × 200 координат вокруг выбранной точки; при переходе по ссылке окна используются её границы. Для новых задач нужен аналитик или администратор проекта local.

Нажмите «Запустить расчёт поля». Сайт показывает реальные стадии: в очереди, расчёт, проверка результата, готово. Процент не имитируется. `job_id` сохраняется в адресе; обновление страницы восстанавливает задачу. Ошибка связи не означает остановку вычисления. После неопределённой ошибки отправки «Повторить отправку расчёта» использует прежний запрос и ключ. Подтверждённый отказ 4xx позволяет исправить границы и создать новую попытку.

«Открыть результат расчёта» ведёт к конкретному `run_id`, исходному SHA и границам. Температура, фон, разность и score используют существующие графики, числовой инспектор и маски. После проверки состава сохраните кейс и скачайте автономный пакет. Задание и числовой результат можно повторно открыть из `/system`.

Рабочая пара **median_x3 + spatial_z_halo**, |Z| ≥ 3.5. Код закреплён коммитом **237168f4d4a3e11260c9f692880cc477cd7af779**. Это reference/untrained, без обучения, без финальной модели Захара и без подтверждения аварийной точности. Гипотезы зон не становятся экспертными ответами или обучающими метками. Экспертная проверка остаётся независимой.

## Контракт API

Все маршруты требуют существующую серверную сессию. Запросы изменения используют существующую CSRF/мутационную защиту.

- `GET /api/v2/analysis-capability`: доступность закреплённого worker, метод/версия, предел миллиона ячеек и таймаут 180 секунд.
- `POST /api/v2/analysis-jobs`: обязательный `Idempotency-Key` длиной 8–128 символов, тело ниже; ответ 202 с ID, стадией, исходником, окном и версией. Метод/параметры берутся с сервера; произвольные дополнительные поля отклоняются.
- `GET /api/v2/analysis-jobs/{id}`: состояние, стадия, времена, безопасная ошибка, отмена и `run_id` только после успешной публикации.
- `POST /api/v2/jobs/{id}/cancel`: существующая отмена в рамках прав проекта. После завершения результат не переписывается.

```json
{
  "region": {"record_id": "5", "row_start": 360, "row_end": 440, "column_start": 180, "column_end": 240},
  "source_sha256": "SHA ИЗ ПАСПОРТА ИСХОДНИКА"
}
```

Повтор одинакового тела с тем же ключом в рамках проекта/аккаунта возвращает прежнюю задачу, в том числе после завершения и при недоступном worker. Другое тело — 409. Новый неверный SHA — 409; неверные границы — 422; превышение native/halo бюджета — 413; занятая очередь — 429 с Retry-After; недоступный worker или БД — контролируемый отказ. Числовые поля не передаются через JSON задач: после завершения используются `/api/v2/result-runs` и бинарные блоки/точные срезы из существующего контракта.

## Worker и эксплуатация

`compose.platform.yaml` собирает compute-worker через `services/web-api/Dockerfile.worker`, добавляя SciPy 1.18.1 к NumPy 2.4.3. API, stream-worker и backup не получают SciPy. Используемые CPU-модули `fiber` скопированы побайтно, имеют manifest контрольных сумм и закреплённый SHA самого manifest. Git attributes отключают преобразование строк этой копии на Windows. Исходный checkout не содержит LICENSE/COPYING; NOTICE сохраняет происхождение и не приписывает новую лицензию.

Worker читает исходные массивы напрямую и запускает расчёт отдельным Python-процессом. Временный пакет создаётся только в его runtime, валидируется существующим проверенным импортом и публикуется в PostgreSQL-документ и неизменяемые `.npy`. Состояние complete и привязка job → run записываются одной транзакцией с проверкой живого lease, отмены и прав автора. Отмена/потеря lease перед commit откатывают документ и удаляют собственные новые файлы. При выключении worker, отмене и таймауте его вычислительное дерево завершается. Незавершённый ответ не становится результатом.

Сохраняются ограничения: одна активная задача пользователя, максимум две исполняемые и десять ожидающих в проекте. В Compose по умолчанию один compute-worker; общий лимит две задачи не означает, что один процесс параллельно выполняет два расчёта. Полные записи свыше лимита нужно разбить на явные окна; скрытого усечения нет. API дополнительно проверяет существующий halo-бюджет 4 млн ячеек и максимальный пространственный span 200 км.

Capability определяется свежим heartbeat `analysis-worker.json` (до 30 секунд) с ожидаемым ML-коммитом. Worker с другими зависимостями/изменённым pinned-кодом отказывается запускаться. Архив и импортированные результаты доступны независимо от нового worker. ML-сервис 8082 и старые API сохраняются для совместимости; в новый онлайн-расчёт поле через них не отправляется.

Для обновления используйте привычную частную env-конфигурацию и реальные пути архива:

```sh
docker compose --env-file /private/platform.env -p haklolarp-web -f compose.web.yaml -f compose.platform.yaml up -d --build --wait api web worker
```

Не заменяйте env-файл примером и не пересоздавайте volumes. Бинарные массивы, документы результатов и job/result связь покрываются существующим backup. Учётные данные и диагностические файлы из `.runtime` не публикуются. Внешний деплой в этот этап не входит.

## Приёмка и измерения

Серверные проверки используют настоящие дочерние процессы и изолированные схемы PostgreSQL: успешный расчёт, одновременный повтор, запрет роли/проекта, неверный SHA/окно, отмена и истечение lease непосредственно перед commit, отключение автора, остановка worker, таймаут и остановка потомка процесса. Сбой после успешного commit не может перезаписать опубликованный запуск.

Chromium/Firefox/WebKit проходят реальный расчёт, потерю ответа после принятия, ручной повтор без дубля, перезагрузку, переход к точному результату, создание кейса и получение ZIP. Проверяются reduced motion и размеры 320/390/430/1440 px. Сценарий входит в полный GitHub Actions и использует только изолированную QA-схему.

[Числовая сверка и измерения](measurements/online-analysis-six-records.json): окна 64×512 всех шести исходников и большое окно 615×1479 записи 1.csv. Каждый переданный массив и маска совпал с прямым выполнением исходного ML-коммита. Большое окно даёт восемь гипотез зон. Эти результаты проверяют интеграцию и воспроизводимость, не качество обнаружения аварий. Стадия validating может пройти между опросами — интерфейс не задерживает её искусственно.

Условия: Windows, loopback FastAPI/PostgreSQL, один worker, SciPy 1.18.1/NumPy 2.4.3. Время включает очередь, запуск Python и накладные расходы измерителя. Память — sampled peak working set дочернего процесса, без API/worker и без обещания полного пика системы. Это не тест десяти одновременных участников и не p95 общего стенда.

Финальный локальный набор: **88 серверных тестов пройдено, 3 пропущено по условиям окружения; 27 клиентских**, ESLint/TypeScript/production build/OpenAPI. Отдельно Linux-контейнер worker выполнил окно 19 800 ячеек за 1.937 с и подтвердил pinned-код/версии зависимостей. Два прежних рабочих ZIP после обновления совпали побайтно по исходным SHA. Финальный CI подтверждается на опубликованном SHA при передаче; локальные проверки не заменяют GitHub Actions.

Первый CI выявил отсутствие пути импорта сервера в дочернем Python тестов. Launcher теперь явно задаёт доверенный путь пакета; regression-проверка удаляет внешний PYTHONPATH перед настоящим расчётом. Проверки не отключались.

Совместимость с режимом просмотра без PostgreSQL проверяется существующим браузерным сценарием: защищённые capability/job запросы выполняются только при наличии аккаунта. Они не переводят обычный просмотр архива на неработающий экран входа.
