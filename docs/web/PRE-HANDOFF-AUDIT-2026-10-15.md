1. **Лендинг и закрытый архив.** Nginx и API разрешают анонимно только три именованных файла лендинга: два логотипа и `landing/visual-data.json`. Бэкапы, скрытые и произвольные JSON-файлы остаются закрытыми. Хешированные ресурсы сборки кэшируются; ответы API и документы не сохраняются в HTTP-кэше.
2. **Вход.** Видны минимум 12 символов, ссылка принятия приглашения, восстановление доступа и возврат на главную. Отдельные сообщения различают неверные данные, лимит попыток и недоступность сервера, не раскрывая существование аккаунта. Открытая самостоятельная регистрация не добавлялась.
3. **Проверки аккаунта.** Смена пароля и управление сессиями требуют реального пользователя даже в явно включённом изолированном legacy QA-режиме. Заимствована такая же защита, уже появившаяся в `main`; добавлена регрессия.
4. **Телефон.** Исправлено вертикальное растягивание пунктов «Другое», из-за которого переход «Аккаунт» уходил за экран. Открытое меню ограничено высотой экрана и прокручивается; Escape закрывает меню. Устранено переполнение формы смены пароля на 320 px.
5. **Локальная разработка.** Vite направляет API к работающему локальному proxy на 8081. Origin переписывается только для совпадающего loopback-источника; чужие источники не маскируются. Добавлены недостающие типы Node для сборки конфигурации.
6. **Регрессии CI.** Обновлены проверки названия и лендинга. Мобильный сценарий теперь действительно нажимает «Аккаунт», проверяет страницу и возвращается к сохранённому паспорту; простого наличия ссылки больше недостаточно. Эти обновлённые сценарии ещё должны пройти CI после публикации.

## Как устроен нормальный вход

1. Первый администратор создаётся оператором через существующую CLI-команду `python -m workbench.accounts <логин> --name "<имя>"` в окружении **нужной БД**. Пароль вводится интерактивно; встроенного пароля нет. На существующем стенде сначала проверяют имеющиеся аккаунты, а не создают новую базу.
2. Администратор в разделе «Аккаунт» создаёт приглашение с проектом и ролью. По умолчанию — `viewer`; приглашение администратора требует подтверждения текущим паролем.
3. Участник открывает персональную ссылку, выбирает логин и собственный пароль. Секрет приглашения находится во fragment, очищается из адресной строки и передаётся в POST. Открытие ссылки не расходует приглашение; создание аккаунта и потребление выполняются атомарно.
4. Вход выдаёт отзываемую серверную сессию в HttpOnly-cookie, а не JWT в localStorage. Для production обязательны HTTPS и Secure-cookie. Абсолютный срок — 12 часов, бездействие — 30 минут. Есть предупреждение и список активных сессий.
5. При потере пароля администратор проверяет участника по известному каналу и выдаёт одноразовую ссылку на 30 минут. После восстановления все старые сессии отзываются. Почтовый сервис не нужен.

Без сессии доступны лендинг, вход, принятие приглашения, восстановление и необходимые опубликованные ресурсы. Рабочие страницы направляют на `/login?next=...`, закрытые API возвращают 401. Безопасный `next` восстанавливает только внутренний маршрут. При недоступности PostgreSQL нет перехода к анонимному имени эксперта. Redis нужен для ограничителя входа: при его отказе новый вход возвращает 503.

Матрица доступа остаётся серверной: viewer читает, analyst/admin создают работы и расчёты, expert сохраняет ответы в своём журнале; административные операции требуют admin. Проверяются проект и конкретные связанные документы. Имя, введённое в браузере, не назначает авторство.

## Блокеры перед merge, запускающим автодеплой

### 1. Согласовать фактический путь обновления

В полученном `main` workflow вызывает `ops/deploy-main.sh`. Тот использует `compose.web.yaml + compose.platform.yaml`, **не подключает** `compose.team.yaml` и допускает `DTS_PLATFORM_ENABLED=false`. Наличие БД по умолчанию не гарантирует Secure-cookie, production-режим, точные Host/Origin, доверенный proxy и резервную копию перед обновлением.

После запуска скрипт вызывает `curl --fail /api/v2/health/ready` без сессии. В закрытой версии ответ 401 ожидаем; такая проверка ошибочно объявит защищённый запуск неуспешным. Убирать авторизацию с readiness ради зелёного деплоя нельзя. Проверять БД/worker следует из контейнера/внутреннего контура, а снаружи — обязательный отказ анонимному API и health с `access_mode=closed-team` и итоговым SHA.

**Требуемая интеграция:** сохранить управление Git/tmux у Григория, направить применение обновления через проверенный закрытый путь `ops/deploy-web.sh`, согласовать private env и проверку результата. Не заменять новые инфраструктурные файлы старой копией целиком. Отдельно проверить, не затронет ли `--remove-orphans` необходимые stream/ML-контейнеры.

### 2. Согласовать ML-сервис после объединения Compose

В текущем локальном `compose.team.yaml` есть ссылка на `ml-compat`, определение которого наследуется из прежнего `compose.platform.yaml`. В новом `main` этот сервис удалён, worker направлен к внешнему ML API. Поэтому **нельзя обещать, что простое добавление team overlay к новому main уже достаточно**. Нужно явно выбрать существующий ML endpoint либо самодостаточное определение compatibility-сервиса и проверить итоговый `docker compose config`. Отказ ML не должен открывать архив или отключать вход.

### 3. Проверить постоянные тома и HTTPS на реальном хосте

До любых изменений оператор сверяет Compose project name, тома PostgreSQL/runtime, миграции, существующие аккаунты и делает резервную копию. Не использовать `down -v`, не пересоздавать пользователей и не автоматически приписывать исторические имена аккаунтам. Текущий HTTPS на внешнем URL сам по себе не доказывает правильные Secure-cookie и доверие proxy внутри контейнера.

В [CLOSED-TEAM.md](CLOSED-TEAM.md) есть подготовленная конфигурация и команды. Read-only проверки оператора:

```sh
bash scripts/verify-team-deployment.sh --inventory
bash scripts/verify-team-deployment.sh --preflight
# После отдельно согласованного обновления:
bash scripts/verify-team-deployment.sh --verify
```

Перед ними устранить описанное расхождение ML-сервиса в итоговом объединённом дереве. Private env хранится вне Git, не публикуется в отчёте. Вывод `docker compose config` с подставленными секретами в чат/артефакты не загружать; использовать `config -q` и безопасную сводку.
