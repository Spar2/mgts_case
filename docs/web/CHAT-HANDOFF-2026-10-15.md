## Правила пользователя

- **Один агент**, без субагентов и делегирования в другие чаты. Пользователь прислал single-agent AGENTS; не возвращаться к старой схеме Sol → Muse → Grok.
- Не делать push, merge, deployment «просто так». Сейчас новые изменения не опубликованы. Ранние разрешения публикации относились к прежним этапам и не отменяют актуальное ограничение.
- Сохранять незакоммиченные изменения, чужие ветки, аккаунты, журналы, тома и артефакты. Не использовать reset/clean, `down -v` и массовую очистку Docker.
- Больше конкретной работы и проверки, меньше предложений новых направлений. До хакатона ограниченное время; нужна связность реальных данных и готовность команды.
- Выводы Muse/Grok/других моделей и старые документы могут ошибаться. Код, фактический запуск и измерения важнее прежних утверждений.
- Не выдавать синтетику, reference-медиану или агентские ответы за финальную модель/человеческий эталон. Отсутствие результата показывать явно.

Актуальные инструкции пользователя имеют приоритет над историческими памятками. При открытии вложенного каталога прочитать применимый `AGENTS.md`. Не переносить из старых сессий доступ к аккаунтам, разрешение на публикацию или решение о выборе модели как бессрочное согласие на новые действия.

## Проект и люди

Репозиторий: `https://github.com/werd0y45/haklolarp`. Хакатонный кейс МГТС — анализ данных распределённых волоконных сенсоров. Исходные шесть CSV — температура по времени и расстоянию. Задача продукта: настоящее измерение → исследование → фактическая обработка → независимый экспертный ответ → неизменяемый проверяемый кейс и автономный пакет.

Тихон/пользователь отвечает за frontend, Захар — ML, Григорий/Гриша — инфраструктуру. Имена, роли и биографии для публичного блока команды пока не согласованы: не выдумывать. Захар занят; нужны понятные инструкции, форматы данных и пригодные для его модели правила интерфейса.

Видимое название заменено на **«Единая аналитическая платформа сенсорных данных»**. DTS Workbench остаётся историческим техническим именем в старых документах/контрактах; служебные форматы ради ребрендинга не менять.

Отличительная ценность проекта — передача воспроизводимого разбора специалисту: выбранные измерения, конкретная обработка, происхождение и экспертная ревизия связаны проверяемыми идентификаторами. Красивое изображение графика не заменяет числовой пакет.

Три сценария продукта:

1. **Работа:** исходное окно → совместимый расчёт → неизменяемое экспертное задание → самостоятельный ответ → кейс → автономный ZIP.
2. **Лаборатория:** два совместимых результата → общая область → сравнение доступных слоёв и происхождения → точные значения → работа.
3. **Мониторинг:** replay настоящей записи → подтверждение сохранения → наблюдение → явный расчёт интервала → работа → кейс.

Оборудование, автоматические аварийные оповещения, обучение новой модели и многопроектная загрузка произвольных CSV не считаются выполненными по наличию кнопок или макетов.

## Архитектура и уже реализованные функции

Frontend — React 19, TypeScript, Vite 8, Carbon React/Sass, IBM Plex, React Router, TanStack Query/Virtual, Motion, uPlot и специализированное Canvas/WebGL-поле; бинарные блоки и worker вместо всей матрицы в React-state. Node 24, npm; версии закреплены lockfile.

Backend — `services/web-api`, FastAPI, NumPy/mmap, PostgreSQL для аккаунтов и постоянных документов, Redis для ограничителя и инфраструктуры, отдельные compute/stream workers, Redis/ClickHouse для подтверждённого replay. Gateway не раскрывает браузеру токены приёма данных и доступ к БД.

| Маршрут | Что в нём |
| --- | --- |
| `/` | Публичный лендинг, ограниченный опубликованный пример; не открытый архив |
| `/login`, `/activate`, `/recover` | Вход, приглашение, восстановление |
| `/works`, `/works/:id` | Сохранённая работа: источник/SHA, окно, профиль/точка, результаты, история, задания и кейсы |
| `/research` | Реальное поле, точный пространственный профиль и временной ряд, inspector, replay, очистка и явный расчёт |
| `/review` | Независимый ответ, короткий режим, отдельные skip/unknown, ревизии/конфликт |
| `/laboratory`, `/experiments` | Каталог и исследовательские отчёты с происхождением; нет автопродвижения «победителя» |
| `/monitoring` | Подтверждённое воспроизведение записи, стадии приёма/сохранения/DSP, явный расчёт интервала |
| `/runs`, `/analysis`, `/candidates` | Импорт/запуски, слои и связанные графики, подготовленные окна |
| `/cases`, `/cases/:id` | Неизменяемый снимок, выбранный run и экспертная ревизия, HTML/JSON/ZIP |
| `/cases/:id?present=1&step=0` | Показ зафиксированного кейса на защите, пять шагов |
| `/demo` | Отдельная интерактивная репетиция; не рабочая разметка |
| `/account`, `/system` | Сессии, приглашения/восстановление по правам; состояние системы |

`/try` и `/request-access` в текущем закрытом продукте больше не дают анонимный рабочий путь. Некоторые старые инструкции всё ещё описывают публичное `/try`; не считать их действующей политикой.

Сохранение кейса поддерживает Idempotency-Key: повтор после потерянного ответа должен вернуть тот же снимок. Изменение работы/ответа/расчёта не переписывает старый кейс. Без выбранного `run_id` отчёт показывает исходник; имя метода само по себе не выбирает последний run. Старые ZIP не пересоздавать при улучшении интерфейса.

Основные модули: `charts.tsx`, `explorer.tsx`, `analysis.tsx`, `investigations.tsx`, `reviews.tsx`, `cases.tsx`, `account-security.tsx`, `access.tsx`; серверные `accounts.py`, `account_lifecycle.py`, `access_policy.py`, `platform.py`, `investigations.py`, `cases.py`, `analysis_results.py`, `streaming.py` и `worker.py`.

### Схема потока данных

```text
Браузер React/Carbon
  ├─ маршруты, формы, выбор окна, ограниченный кэш
  └─ worker + TypedArray → Canvas/WebGL/uPlot
                │ запросы /api, бинарные блоки, SSE состояния
                ▼
Nginx → FastAPI gateway → проверка сессии / CSRF / проекта / роли
                ├─ PostgreSQL: аккаунты, документы, ревизии, связи
                ├─ artifacts: неизменяемые массивы, очереди, снимки
                ├─ compute worker: ограниченные фоновые задания
                ├─ ML API / закреплённый analysis runtime
                └─ Redis / ClickHouse / stream worker: replay
```

SSE передаёт состояние, курсор и события; большие числовые поля получают отдельными блоками. Отмена устаревшего запроса и защита от запоздалого ответа обязательны при смене окна, записи и расчёта.

### Инварианты, которые нельзя нарушать

- Идентичность данных задаётся источником и SHA, а не одним именем `5.csv`.
- Наведение курсора не создаёт запись в БД. Контекст работы сохраняется явным действием.
- Задание эксперту — отдельный снимок, не живая ссылка на меняющееся окно работы.
- Пропуск, неоднозначность и неизвестность — разные состояния; до ответа не раскрывать методы и причины отбора.
- После конфликтного сохранения показать актуальную ревизию; не выполнять скрытую перезапись.
- Повтор после неопределённого сетевого исхода использует ту же попытку/ключ. Это отличается от новой операции с другим содержимым.
- Ссылка работы на кейс не даёт права переписать снимок кейса. Если создание кейса прошло, а привязка нет, повторять привязку, а не создавать дубликат.
- Принятие профиля Redis, запись ClickHouse, сверка и DSP — разные стадии. DSP профиля не означает завершённый анализ поля.

## Контракт для Захара и ограничения научных выводов

- Профиль: `dts-method-result-v1`, импорт `POST /api/v1/results`, каталог `/api/v1/runs`. Полная исходная пространственная ось одной строки, °C/null; запрос до 256 KiB. [RESULT-HANDOFF](RESULT-HANDOFF.md).
- Поле: **`dts-analysis-result-v2`**, `manifest.json`, исходные `x_m.npy`, `time_s.npy` Float64; необязательные processed/background/score и bool-маски, zones.json. Форма `[время, расстояние]`, полуоткрытые исходные индексы, SHA, версия/параметры/происхождение. Импорт операторский с явным проектом и существующим author ID. [ANALYSIS-CONTRACT](ANALYSIS-CONTRACT.md).
- `/api/v2/result-runs` и detail/tiles/slices/zones используют авторизацию, исходные координаты, ограниченные блоки и реальные значения.
- Не подменять координаты, не переносить начало времени на начало окна, не угадывать часовой пояс. Sentinel `-300` — не температура; заполненный алгоритмом пропуск не становится реальным наблюдением.
- Разность показывает изменение сигнала, score — заявленную оценку метода; без эталона ни то ни другое не доказывает очистку/обнаружение аварии. Широкое усреднение скрывает пики: различать точку, локальную зону и всё окно.
- Исследования ветки ML уже интегрировались явно закреплёнными снимками, включая исторический `237168f` и real-only цикл. Не подменять runtime после любого нового ML push. Часть ранних CNN/tree — синтетические; это историческое происхождение, не финальная модель.
- Финальный результат Захара для защиты нельзя считать подтверждённым по старым сообщениям. Сначала сверить фактические артефакты, SHA/форму, pinned runtime и docs; при необходимости вновь посмотреть свежую ML-ветку.

Полезные документы: [WORKSPACE](WORKSPACE.md), [ANALYSIS-WINDOWS](ANALYSIS-WINDOWS.md), [ONLINE-ANALYSIS](ONLINE-ANALYSIS.md), [ML-EXPERIMENTS](ML-EXPERIMENTS.md), [CASES](CASES.md), [CASE-PRESENTATION](CASE-PRESENTATION.md).

### Закреплённые версии и исследовательские материалы

В текущем `analysis_compute.py` рабочий reference закреплён за `237168f4d4a3e11260c9f692880cc477cd7af779`, метод — `median_x3+spatial_z_halo`. Real-only исследовательский цикл в документации связан с `1c09476310bbad92cd832dc65cf339aab3bc8e61`; лаборатория проверяет файлы по manifest/SHA и не объявляет его автоматически operational approved.

Это **разные назначения**: закреплённый runtime, импортированный фактический run, исторический отчёт и кандидат в будущую модель. Перед подключением свежих ML-пушей выяснить, что изменилось в каждой категории. Поздний коммит не является доказательством улучшения качества.

Четыре внешние карточки, подписанные в ML-материалах именем Захара, не должны автоматически становиться ответами его действующего аккаунта. Историческое происхождение сохранять; подтверждение автором через рабочий контур — отдельный шаг. Подготовленные 36 карточек — материал для человеческой проверки, не уже выполненная разметка.

## Авторизация и последняя проверка

Существующий реальный контур, а не авторизация с нуля: PostgreSQL-аккаунты, Argon2, одноразовое приглашение → свой пароль → отзываемая HttpOnly-сессия. 12 ч абсолютный срок, 30 мин idle; CSRF, точные Host/Origin, Redis-лимиты, отзыв, смена/восстановление пароля, роли viewer/expert/analyst/admin. Первого admin создаёт операторская CLI с интерактивным паролем, стандартного пароля нет. Открытая регистрация не нужна, почтового сервиса нет.

В командной версии без PostgreSQL запуск/рабочий доступ закрывается, при отказе БД — 503. При отказе Redis новый вход — 503. Без входа разрешены лендинг/вход/приглашение/reset и ровно необходимые опубликованные ресурсы. Рабочие страницы — 303 на login, API — 401. Скрытая кнопка не заменяет серверную проверку.

Локально исправлены точечный allowlist трёх landing assets в Nginx/API, защита account-actions без principal в legacy QA, login helper/ссылки/сообщения, мобильное меню (вертикальный flex-basis растягивал пункты до 120 px), переполнение формы пароля на 320 px, QA-селекторы. Vite proxy направлен к 8081; Origin переписывается лишь для своего loopback origin.

### Нормальный жизненный цикл участника

1. Оператор проверяет существующую БД/аккаунты. Первого администратора создаёт CLI `python -m workbench.accounts USERNAME --name "NAME"` в **нужном** окружении; пароль вводится интерактивно.
2. Admin выбирает проект и роль приглашения, по умолчанию viewer. Admin-приглашение требует текущего пароля администратора.
3. Ссылка действует 24 часа, однократная; в БД только хэш случайного секрета не менее 32 байт. Открытие не расходует приглашение. Создание аккаунта и потребление приглашения атомарны.
4. Участник выбирает логин и пароль минимум 12 символов. Секрет приходит во fragment, удаляется из URL и передаётся POST; не сохраняется в localStorage/логах.
5. После входа безопасно восстанавливается внутренний маршрут. Выход очищает аккаунтные кэши; другая открытая вкладка также теряет доступ.
6. Восстановление: проверка человека администратором по известному каналу, одноразовая ссылка на 30 минут, собственный новый пароль участника, отзыв прежних сессий и reset-ссылок.

Роли не назначаются из браузерного display name. Работы, ответы, расчёты и кейсы относятся к серверному аккаунту и проекту; исторические неподтверждённые имена не приписываются новым аккаунтам автоматически.

### Матрица доступа

| Роль | Рабочие возможности | Что нельзя выводить из роли |
| --- | --- | --- |
| viewer | Читать разрешённые архив, результаты, работы и кейсы проекта | Чтение не даёт создания работы, запуска расчёта или управления аккаунтами |
| analyst | Работы, расчёты, назначения и кейсы по действующим проверкам доступа | Нельзя сохранять ответ как другой эксперт или читать чужой проект |
| expert | Независимые ответы, прогресс, кейс собственного ответа в предусмотренном контексте | Нельзя заранее раскрывать чужой ответ или автоматически создавать эталонную маску |
| admin | Командные действия analyst и управление доступом | Admin не отменяет SHA, совместимость данных и неизменность кейса |

Лимит входа — 5 попыток в минуту на пару IP/логин и 30 на IP; централизован в Redis. Тяжёлые задания — одна активная задача пользователя, две выполняемые и десять ожидающих в проекте; перегрузка возвращает 429 с Retry-After. Не обходить ограничения автоматическими повторами.

## Удалённый стенд и важные блокеры

Гриша сообщил: merge `web -> main` вызывает автодеплой. Адрес `https://xeon-staging.tail5a7687.ts.net/` в последней проверке доступен; только анонимные GET, без входа/записи.

### Что запросить/проверить у оператора без передачи секретов

- Какой SHA реально запущен и какой скрипт вызывает workflow на `main`.
- Compose project name и набор подключённых Compose-файлов/профилей.
- Имена и точки монтирования постоянных томов PostgreSQL и runtime; существующие аккаунты сохраняются.
- Существует ли private team env с точными Host/Origin, production и Secure-cookie; **не запрашивать содержимое секретов в чат**.
- Где завершается HTTPS и на какой loopback target указывает Tailscale Serve; ACL и доверенный proxy соответствуют реальной цепочке.
- Как подключён ML после удаления `ml-compat` из нового main и остаётся ли доступен архив при отказе модели.
- Где лежит зашифрованный backup, отдельный ключ восстановления, как проверено восстановление в новой пустой БД.
- Какая проверка заменяет анонимный readiness: внутреннее подтверждение БД/worker плюс внешний health/SHA и ожидаемый отказ закрытому API.

`docker compose config` без `-q` может распечатать подставленные секреты. В общие логи — только безопасная сводка, `config -q` и нужные несекретные поля. Даже успешный build не даёт права запускать применение.

### Сначала определить, какой сервер нужен

**Вариант A — frontend поверх уже запущенного локального Docker API.** Это текущая схема Vite proxy → 8081. Сначала проверить доступность и режим, не поднимать второй backend поверх существующего:

```powershell
Set-Location C:/dev/mgts/hackathon-delivery
Invoke-RestMethod http://127.0.0.1:8081/api/v1/health |
  Select-Object auth_enabled, access_mode, build_sha, qa_mode
```

Отсутствующее поле — неизвестное значение, не подтверждение нужного режима. Затем в `apps/web` после установки зависимостей по lockfile:

```powershell
npm run lint
npm test
npm run build
# Только если нужный порт свободен и preview действительно требуется:
npm run dev -- --port 8887 --strictPort
```

`npm ci` изменяет локальные зависимости: применять по необходимости, не поверх важных незавершённых процессов автоматически. Не менять lockfile через `--force` или `--legacy-peer-deps` для обхода ошибки.

**Вариант B — отдельный локальный Python API на 8091.** Нужны Python 3.12, зависимости сервера, prepared records/queue, PostgreSQL и безопасная конфигурация. Важная найденная несогласованность: `scripts/start-web.ps1` запускает backend **8091**, а текущий `vite.config.ts` проксирует **8081**. Пока это явно не согласовано, скрипт может поднять один API, а браузер обращаться к другому. Не лечить это отключением авторизации. Выбрать один backend, согласовать proxy/Origin/Host, проверить health и зафиксировать изменение отдельно.

Старый README с запуском API без PostgreSQL также не является актуальной командной конфигурацией. Явный anonymous test bypass допускается лишь в изолированном QA/test-окружении, не как способ запустить общий сайт.

### Серверные тесты и OpenAPI

В CI используются Python 3.12 и `requirements.worker.txt`, свежие PostgreSQL/Redis, затем `pytest services/web-api/tests -q` и OpenAPI drift check. Реальные записи для полного локального набора задаются отдельно; их отсутствие может приводить к skips.

Не направлять тестовые мутации в рабочую БД. Для повторения сначала подготовить отдельные credentials/БД/namespace и проверить QA-маркеры. Не запускать браузерные QA-скрипты на произвольном адресе: в них технические сохранения, приглашения и другие операции. Тестовые ответы не являются человеческим эталоном.

Типы клиента генерируются через `npm run generate:api` из `services/web-api/openapi.json`; при изменении контракта сначала обновить серверную схему, затем типы, проверить drift. Последний аудит маршруты/форматы не менял.

## Ближайшие действия

1. Закончить фактическую визуальную сверку белой версии с изображением пользователя: body white, рабочие panels gray, тёмная оболочка; не менять palette/masks/data. Проверить desktop/mobile и нужный запущенный адрес.
2. Передать Захару `STYLE-AND-IDENTITY.md`, а для данных — `ANALYSIS-CONTRACT.md`. Файлы входят в публикационный пакет; доступность проверять по ветке `sol-web-design-handoff`, не по старому checkout команды.
3. Если пользователь отдельно запросит актуальный Pen/PNG — создать или синхронизировать по конкретной текущей версии кода. Без такого запроса архив не открывать. Видео не загружать в Git.
4. Согласовать с Гришей безопасный путь автодеплоя и ML Compose в итоговом дереве. После отдельного разрешения — понятный commit/PR, проверки итогового SHA, затем merge/deploy и проверка фактического стенда. Пользователь отдельно разрешил собрать и загрузить пакет в Git; применение на сервере и merge в main этим не выполняются.
5. Не расширять сайт ещё одним набором фич до завершения этого пути. Дополнительные тексты старых README о public demo, неподтверждённых именах и multi-model pilot исторические, а не текущие правила.

### Финальная приёмка передачи

- [ ] Новая версия страницы действительно показана и сверена с образцом, а не только собрана.
- [ ] Понятно, где опубликован код, какой SHA проверен и какой SHA реально запущен.
- [ ] Лендинг открывается анонимно; весь рабочий API и скачивания требуют доступа.
- [ ] Приглашение, вход, выход, истечение/отзыв, восстановление и переключение аккаунтов не оставляют чужие данные в кэше.
- [ ] Авторство и права проверены двумя участниками; отсутствуют обходы через прямой маршрут/API.
- [ ] Работа → расчёт → экспертное задание → ответ → кейс → ZIP проходят на реальных данных.
- [ ] При недоступности PostgreSQL/Redis нет анонимного обхода; при недоступности ML архив остаётся доступен авторизованному участнику.
- [ ] После перезапуска/обновления сохранены аккаунты, работы, ответы, run ID, SHA и старые ZIP.
- [ ] Проверки относятся к итоговому коммиту; ограничения браузерной/нагрузочной приёмки указаны честно.
- [ ] Команда получила инструкции и локальный/автономный резерв для защиты.

Ни один пункт этого списка не отмечен автоматически прежними тестами. Часть уже подтверждена локально, но финальная формулировка включает фактический командный стенд.
