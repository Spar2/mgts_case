# Подключение результатов Захара

10 октября 2026. Этот адаптер упаковывает **уже выполненный расчёт**. Он не обучает модель, не создаёт веса и не вычисляет качество.

## Что передать

Из паспорта исходника возьмите его SHA и исходные индексы участка (конец не включён). Подготовьте `metadata.json`:

```json
{
  "schema_version": "dts-method-result-v1",
  "region": {"record_id": "5", "row_start": 0, "row_end": 1, "column_start": 0, "column_end": 2364},
  "source_sha256": "ЗАМЕНИТЬ НА SHA ИЗ ИСХОДНИКА",
  "method": "zakhar-method",
  "method_version": "ЗАМЕНИТЬ НА COMMIT ИЛИ SHA АРТЕФАКТА",
  "parameters": {},
  "calculated_at": "2026-10-10T12:00:00+03:00",
  "training_origin": "unknown",
  "limitations": "Независимая точность не установлена"
}
```

Индексы выше — только пример структуры, не готовый расчёт: укажите реальные границы, версию, параметры, время и происхождение. `training_origin`: real / synthetic / mixed / untrained / unknown; сайт показывает заявленное автором происхождение, а не сертифицирует его.

В `actual-result.json` должен лежать фактический результат метода, например объект с `denoised` — массивом температур/`null`. Здесь готового массива нет, чтобы не подменять расчёт Захара.

Для `denoised` допускается **ровно один исходный профиль**: `row_end = row_start + 1`, массив на всю пространственную ось записи, исходный порядок, °C. Даже если метод заполнил пропуски, отображение возвращает исходную маску качества. `null` метода остаётся пропуском; sentinel не превращается в температуру. Для результата участка без профиля допустим объект `zones` и дополнительные сведения: пока это проверяемая сводка/JSON, а не произвольная координатная overlay. Неизвестную систему координат сайт не угадывает.

## Упаковать и проверить

В окружении веб-сервера с установленными зависимостями:

```text
python scripts/package-method-result.py --records /path/to/prepared/records --metadata metadata.json --result actual-result.json --output result-handoff.json
```

Проверяются схема, SHA, границы, форма профиля, конечность чисел и размер. Подготовленные массивы открываются read-only; существующий выходной файл не перезаписывается. Максимум файла для UI — 240 KiB, запроса — 256 KiB. Большой результат требует отдельного бинарного адаптера: **не сокращайте массив и не удаляйте происхождение ради лимита**.

## Импортировать и показать

Обычное исследование также поддерживает подключение сохранённого профиля: откройте «Исследовать участок» у нужного запуска либо выберите расчёт в карточке участка. Видимый ID относится и к графику, и к отчёту. Сохранённый паспорт фиксирует этот выбор; изменение профиля/области/метода его сбрасывает.

**Изменение `/api/v1/reports`:** необязательный `run_id` выбирает конкретный результат. Без него отчёт содержит исходный сигнал, даже если передан `method`. Название метода больше не выбирает последний расчёт автоматически. Несовместимый результат возвращает 409, отсутствующий — 404, чужой проект — 403; замены другим результатом нет. `/denoise` возвращает `run_id` дополнительно к прежним полям. Экспертный ответ включается только по прежнему проверенному контексту.

1. Завершите репетицию кнопкой в синей полосе. Нужна роль analyst/admin.
2. В «Запусках» импортируйте `result-handoff.json`. Сервер повторно сверит источник и форму. Это импорт результата, не весов.
3. Откройте репетицию подходящего окна. На шаге «Сравнение» обновите список результатов и выберите импортированный метод.
4. Для результата профиля выберите именно его исходный индекс. Доступны только совместимые источник/SHA/границы; чужой результат отклоняется сервером.
5. Подключите результат. Профили имеют согласованные шкалы и связанный курсор; разность не объявляется доказанным шумом. В автономный отчёт войдёт фактически выбранная обработка.

Если расчёт относится к другой записи/версии, нужно открыть соответствующий исходник, а не переименовывать SHA. Если веса остаются на ПК Захара, сайт может работать с его подготовленным результатом. Для выполнения модели на сервере понадобится отдельная интеграция её настоящего runtime и ресурсов; этот этап её не имитирует.

## Независимо сверить скачанный отчёт

Для обычного исследования есть офлайн-проверка, которая не требует запущенного сайта, аккаунта или БД. Нужны зависимости веб-API, скачанный `dts-evidence.json` и каталог **одной подготовленной записи**, содержащий `manifest.json`, native-массивы и `profiles.json`.

```text
python scripts/verify-evidence.py --record /path/to/records/record-cache-id --report dts-evidence.json
```

Если выбрана обработка, дополнительно сохраните JSON ответа `GET /api/v1/runs/{видимый ID}` в своём авторизованном браузере: откройте запрос в Network → Response и сохраните **только ответ JSON**. Не передавайте HAR, cookie, заголовки авторизации или browser storage. Это полный сохранённый запуск с `id`, `status`, метаданными и `result`, а не исходный файл импорта.

```text
python scripts/verify-evidence.py --record /path/to/records/record-cache-id --report dts-evidence.json --run selected-run.json
```

Код возврата 0 и `verified=true` подтверждают совпадение SHA, границ, временных метаданных, точного профиля, координат, маски, статистик окна и обзорных значений. Для обработки также сверяются выбранный ID, покрытие, полный результат и метаданные происхождения; исходные пропуски и `null` метода сохраняются. Нет выбранного результата — файл запуска не нужен. Есть результат, но файл запуска не передан — проверка завершается ошибкой, не ослабляя проверку до одних метаданных.

Вывод содержит SHA файлов для последующей сверки и числа проверенных точек, без температур и экспертного текста. Утилита ничего не записывает и не обращается к сети. Она поддерживает JSON **обычного исследования**, не форматы `/demo` и `/try`, и не проверяет HTML. Это проверка согласованности относительно переданных исходников: она не является цифровой подписью, не подтверждает авторство ответа и не оценивает качество модели. Сохраняйте исходные HTML/JSON и файл запуска вместе; не заменяйте их снимком экрана.
