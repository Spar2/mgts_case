# Оператор: локальная приёмка production-конфигурации

Этап готовит конфигурацию к общему стенду. Внешняя публикация, DNS, реальные
сертификаты и открытие сетевого доступа выполняются отдельным шагом. Сейчас
HTTPS-порт привязан к loopback. Проект использует React/Carbon, FastAPI,
PostgreSQL и общий Redis; Redis/БД/API не публикуются наружу.

## Конфигурация и запуск

Нужен Docker Compose с поддержкой `!override`/`!reset`. Создайте приватный
env-файл вне Git (`umask 077` на Linux). Укажите:

```dotenv
DTS_POSTGRES_PASSWORD=replace-with-a-random-private-password
DTS_RECORDS=/absolute/path/to/prepared/records
DTS_QUEUE=/absolute/path/to/verified/queue
DTS_RESEARCH_PACK=/absolute/path/to/real-data-v2
DTS_PUBLIC_HOST=localhost
DTS_PUBLIC_ORIGIN=https://localhost:8443
DTS_TLS_PORT=8443
DTS_TLS_DIRECTORY=/absolute/private/path/to/tls
DTS_BACKUP_DIRECTORY=/absolute/private/path/to/encrypted-backups
DTS_BACKUP_RECIPIENT=age1-public-recipient-generated-off-server
```

В каталоге TLS нужны `fullchain.pem` и `privkey.pem`. Для локальной приёмки
используйте отдельный временный сертификат с SAN `localhost`/`127.0.0.1`.
Для последующего реального стенда задайте точные Host и HTTPS Origin (с портом,
если он нестандартный), реальные сертификаты и согласованное сетевое размещение.
Внутренний proxy — `172.30.89.10`, сеть — `172.30.89.0/24`; проверьте, что она
не конфликтует с другими сетями. Uvicorn доверяет forwarded-заголовкам только
этому proxy. Nginx перезаписывает клиентский `X-Forwarded-For`.

```sh
docker compose --env-file /private/workbench.env -p haklolarp-web \
  -f compose.web.yaml -f compose.platform.yaml -f compose.production.yaml config -q
docker compose --env-file /private/workbench.env -p haklolarp-web \
  -f compose.web.yaml -f compose.platform.yaml -f compose.production.yaml \
  --profile maintenance up -d --build web api worker backup
```

Большой архив и очередь монтируются read-only. Публичный пакет уже включён в
образ: `services/web-api/public/demo-v1`. Посетитель читает только его;
публичный маршрут не обращается к рабочему Store. При отсутствии ML публичное
окно продолжает работать: результаты не рассчитываются по запросу посетителя.

Production требует PostgreSQL; при его недоступности закрытый контур отказывает.
При отказе Redis попытки входа/активации/восстановления возвращают 503 с
`Retry-After`. Общий токен команды и localStorage JWT не используются.
Cookie сессии: HttpOnly, Secure, SameSite Strict; мутации закрытого контура
требуют CSRF-токен. Host/Origin задаются явно, произвольные значения отклоняются.

## Первый администратор и аварийное восстановление

```sh
docker compose --env-file /private/workbench.env -p haklolarp-web \
  -f compose.web.yaml -f compose.platform.yaml -f compose.production.yaml \
  exec api python -m workbench.accounts operator --name 'Имя администратора'
```

Пароль вводится интерактивно, дважды. Не передавайте его в командной строке.
Для существующего администратора добавьте `--recover`. Команда сохраняет ID,
членства и авторство разметки, меняет пароль, включает аккаунт, отзывает сессии
и ссылки восстановления, добавляет событие аудита. Это локальный операторский
доступ к БД, а не публичный способ обойти приглашение.

## Миграции и очереди

`workbench/migrations.py` содержит упорядоченные аддитивные миграции 2 и 3.
Они выполняются транзакционно под advisory lock схемы; пользователи и журналы
не пересоздаются. Старые четыре столбца сессии сохранены, добавлены время
создания/последней активности и описание. Миграция 3 добавляет отправителя
задания для пользовательской квоты.

На пользователя допускается одно queued/running задание; в проекте — две
исполняемые и десять ожидающих. Проверки сериализуются блокировкой проекта,
claim — транзакционной блокировкой планировщика. Повтор того же ключа
идемпотентности возвращает существующую задачу; другое содержимое — 409.
Перегрузка — 429 с `Retry-After: 10`. Lease, отмена и ограждение результатов
старого worker сохранены.

Nginx ограничивает тела 64 KiB, **только** `/api/v1/results` допускает 256 KiB.
Это совпадает с контрактом API; увеличение не распространяется на приглашения,
заявки и остальные маршруты.

## Резервные копии

Сгенерируйте age-identity на отдельной операторской машине. На сервер передайте
только публичного получателя `age1…`; приватный ключ не монтируйте в backup-job.
Он нужен оператору при восстановлении и должен храниться отдельно от копий.

`workbench.backup_job --daily` проверяет день UTC ежечасно, делает одну копию
в день и хранит последние семь **успешно зашифрованных** архивов
`dts-YYYY-MM-DD.tar.age`. Сначала строится согласованный repeatable-read снимок,
проверяются SHA immutable-артефактов, затем выполняется age и атомарная
публикация. Plaintext существует во временном tmpfs и удаляется. Ошибка не
удаляет старые копии; процесс повторяет попытку через пять минут.

Копируются проекты, аккаунты с хэшами паролей, членства, документы, ревизии,
идемпотентность, аудит, задачи, заявки, приглашения и восстановления. Сессии
не копируются. При восстановлении все ссылки приглашения/восстановления
принудительно отзываются, незавершённые задачи становятся failed.

Скопируйте зашифрованные архивы на независимое хранилище через доверенный
канал (например, SFTP/rsync). Делайте это отдельным системным job, проверяйте
успешность передачи и держите копию ключа офлайн. Семь локальных файлов не
заменяют копии вне сервера. Исходные CSV/NPY и ClickHouse — отдельные большие
хранилища; их копирование не входит в snapshot управляющего контура.

```sh
age -d -i /private/operator-identity.txt -o /private/snapshot.tar dts-YYYY-MM-DD.tar.age
mkdir /private/decrypted
tar -xf /private/snapshot.tar -C /private/decrypted
# Создайте НОВУЮ ПУСТУЮ БД и отдельный каталог runtime, затем:
DTS_DATABASE_URL=postgresql://.../new_empty_database \
DTS_RUNTIME=/private/new-runtime \
python -m workbench.maintenance restore /private/decrypted/snapshot
```

Не восстанавливайте поверх рабочего контура. Команда отклоняет непустую цель
и сверяет SHA файлов/артефактов. После проверки удалите временный plaintext
операторским безопасным способом. Повторный вход и выдача новых приглашений
нужны явно; сохранённые ID авторов и ревизии должны совпасть.

## Наблюдаемость и действия при сбое

`/api/v2/metrics` доступен администратору: количество запросов/статусы,
суммы задержек и накопительные buckets 10/50/100/500/1000/5000 ms, состояния
очереди, возраст последней успешной копии. Счётчики запросов относятся к одному
API-процессу; очередь и backup-marker общие. OTLP можно подключить существующим
`OTEL_EXPORTER_OTLP_ENDPOINT`. Для нескольких процессов агрегируйте их метрики.

Логи содержат ID запроса, шаблон маршрута, HTTP-статус и длительность. Пароли,
cookie, токены, query strings и тела запросов не записываются. Отказы входа и
ограничителя видны по статусам 401/429/503. Не включайте debug-логирование тел.

Проверяйте readiness worker и возраст копии; отсутствие свежей копии — повод
проверить recipient, место и доступность БД. При 429 не повторяйте запрос
без задержки. При 503 исходное публичное окно может оставаться доступным,
но вход и сохранение должны явно показывать ошибку, а не имитировать успех.

Правила одноразовых ссылок и сессий основаны на
[OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
и [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
