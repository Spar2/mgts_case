# P5 — P1-cycle runbook (DEV-CLONE → DATA-SAFETY → DOCS)

Цель цикла: влить три независимых пакета на базу `origin/main` `80a3633`
без расщепления деплой-контрактов P4 и без расширения триггеров.
Каждый пакет вливается отдельно, каждый откатывается одной revert-коммитом.

База: `origin/main` = `80a3633` (`fix(merge-train): ansible-lint gate covers data-stand.yml`).
Порядок вливания строгий: **DEV-CLONE → A → B → DOCS**.

## 1. Пакеты

| Пакет | Состав | Подход (зафиксирован) |
|---|---|---|
| PKG-1 DEV-CLONE | dev-клон деплоя: скрипт, workflow-вызов, sparse checkout, cleanup-гварды | **externalize** как `dev-opt-test1`: скрипт `.github/scripts/dev-clone-deploy.sh` + sparse checkout + `vars.TOPIC` + cleanup-гварды; **инлайн-порт отклонён** (дублирует canon-логику в caller, расходится при первом же изменении canon) |
| PKG-2A DATA-SAFETY | гарды стека: `verify.py`, `stream-all.sh` | гарды поверх существующего `stack/compose.yaml`; поведение стека не меняют, только валят прогон при нарушении инвариантов |
| PKG-2B DATA-SAFETY | миграции: `v2.sql` → `migrations/` + quoting раннера | раскладка `v2.sql` по версионированным миграциям + чинка quoting в раннере миграций (падение было на кавычках, не на SQL) |
| PKG-3 DOCS | `CONTRACTS.md` + `check.sh` | **строго после A/B**: контракты фиксируют итоговое состояние гардов и миграций, не промежуточное; `check.sh` — машинная сверка репо с контрактами |

### 1a. PKG-1 DEV-CLONE (externalize, не инлайн)

- Скрипт `.github/scripts/dev-clone-deploy.sh` — вся логика клона в одном
  месте, caller только вызывает с `TOPIC` из `vars.TOPIC`.
- Sparse checkout — клон тянет только нужные пути, а не всё дерево.
- Cleanup-гварды — удаление только `pr-<N>`-скоупа (`-p haklolarp-pr-<N>`,
  единственный санкционированный `--volumes`, по P4 §5); запрет на `rm -rf`
  вне preview-префикса.
- Инлайн-порт (копипаст шагов `dev-opt-test1` прямо в caller) отклонён:
  две копии canon-логики расходятся молча, чинить придётся дважды.

### 1b. PKG-2A DATA-SAFETY (гарды)

- `verify.py` — инварианты стека после подъёма (порты loopback, проект
  `haklolarp-stack`, тома на месте). Fail-closed: нарушение = красный прогон.
- `stream-all.sh` — единый сбор логов/дампов стека для `report`-дайджеста
  (контракт P4 §6: один digest на прогон, артефакты вместо спама).
- Режимы `report`/`muts`/`streams` только читают; `truncate`/`purge`
  (`stack/verify.py`) и `stack/stream-all.sh` деструктивны — только
  с `--yes`/`CONFIRM=1`, без подтверждения — отказ (fail-closed,
  детали в пометке §3).

### 1c. PKG-2B (миграции + quoting)

- `v2.sql` раскладывается в `migrations/` как версионированные файлы
  (`V<n>__*.sql`); монолит `v2.sql` после раскладки удаляется.
- Quoting раннера чинится отдельно от SQL-содержимого: сначала зелёный
  прогон существующих миграций через починенный раннер, потом новые файлы.
- Порядок внутри B: раннер → раскладка → прогон с нуля + прогон поверх
  существующей БД (идемпотентность).

### 1d. PKG-3 DOCS (после A/B)

- `CONTRACTS.md` — зафиксированные контракты: что гардируют A-гарды,
  какая раскладка миграций считается каноном, какие проверки делает `check.sh`.
- `check.sh` — локально запускаемая сверка (репозиторий ⇄ контракты),
  ноль внешних зависимостей.
- Вливается последним: контракты, написанные до A/B, фиксируют промежуточное
  состояние и устаревают в день вливания.

## 2. Порядок вливания и DEP-рёбра

Строгий порядок: **DEV-CLONE → A → B → DOCS**.

- **S-1 DEV-CLONE.** DEP: нет (только база `80a3633`). Новый скрипт + вызов,
  существующих caller'ов не касается.
- **S-2 A (гарды).** DEP: S-1 (dev-клон не должен молча проходить сломанный
  стек; гарды должны существовать до того, как B начнёт двигать SQL).
- **S-3 B (миграции + quoting).** DEP: S-2 (миграции бегут под гардами;
  сломанная миграция = красный прогон, а не тихая порча данных).
- **S-4 DOCS.** DEP: S-2 + S-3 (контракты описывают итог, §1d).

Правила серии: один пакет — один PR/коммит-серия; следующий пакет стартует
только после зелёных гейтов предыдущего; canon-поведение (`deploy-reusable`,
имена workflow/group из P4 §4) не меняется ни в одном пакете.

## 3. Матрица верификации

| # | Проверка | Команда | Ожидание |
|---|---|---|---|
| V1 | YAML-парс всех touched workflow | `python3 -c "import yaml,glob; [yaml.safe_load(open(f)) for f in glob.glob('.github/workflows/*.yml')]"` | без исключений |
| V2 | `py_compile` гардов | `python3 -m py_compile stack/verify.py` | exit 0 (только синтаксис; рантайм-подкоманды `truncate`/`purge` — деструктивные, см. пометку под матрицей) |
| V3 | `shellcheck` скриптов | `shellcheck .github/scripts/dev-clone-deploy.sh stack/stream-all.sh ansible/check.sh` | без error; тулы нет в окружении — только честный SKIP с пометкой в отчёте, иначе блокер |
| V4 | `actionlint` workflow | `actionlint .github/workflows/dev-clone.yml` | без error; тулы нет в окружении — только честный SKIP с пометкой в отчёте, иначе блокер |
| V5 | `check.sh` сходится | `bash ansible/check.sh` | exit 0 на чистой базе + влитые пакеты |
| V6 | миграции с нуля | прогон миграций на пустой БД | exit 0, `verify.py` зелёный после |
| V7 | миграции поверх живой БД | прогон миграций на БД с данными P3 | exit 0, данные целы, `verify.py` зелёный |
| V8 | cleanup-гварды | dry-run клона + `rm -rf` вне preview-префикса | отказ (nonzero), preview-скоуп удаляется |
| V9 | триггеры не расширены | `git diff --stat` по `.github/workflows/` | нет новых `branches:`/`paths:` вне dev-клона |
| V10 | docker-гейты | compose-подъём стека | где docker есть — зелёный; где нет — **честный SKIP** (зафиксировать в отчёте, не рисовать зелень) |

V6/V7 — критерий именно B: оба прогона зелёные, иначе B не влито.

Пометка о деструктивности (читать перед запуском V2/V6/V7):
`stack/verify.py` — НЕ read-only гард: подкоманды `truncate`/`purge` выполняют
`TRUNCATE TABLE` и чистку стримов, запуск только с `--yes`/`CONFIRM=1`, без
подтверждения — отказ (fail-closed). `stack/stream-all.sh` — НЕ read-only гард:
трёт таблицы CH (`truncate`) и `DEL`-ит стримы `dts:*`, без `--yes`/`CONFIRM=1` —
`DRY-RUN refuse` (exit 2, fail-closed). В V2 выполняется только `py_compile`
(синтаксис, без рантайма); любой рантайм-вызов `verify.py`/`stream-all.sh` вне
V6/V7 — запрещён.

Гарды fail-closed: каждый шаг V1–V10 — блокер; SKIP допустим только там, где
матрица его прямо разрешает (V3/V4/V10), и только с явной пометкой в отчёте
(`SKIP: <тул> отсутствует в окружении`). Немаркированный SKIP = красный прогон.

## 4. Критерии перехода к деплояторам

Пакет считается влитым и цикл переходит дальше, когда одновременно:

1. V1–V2 зелёные всегда (V2 = `python3 -m py_compile stack/verify.py`, только
   синтаксис); V3–V4 зелёные, SKIP — только с явной пометкой об отсутствии тулы
   в окружении, иначе блокер. Немаркированный SKIP = красный прогон.
2. V5 зелёный (`bash ansible/check.sh`; сам `ansible/check.sh` fail-closed:
   без shellcheck — exit 1, а не silent-pass) — только для S-4; для S-1–S-3 —
   N/A, фиксируется в отчёте.
3. V6–V7 зелёные (только для S-3; блокер вливания B).
4. V8 зелёный (только для S-1).
5. V9 зелёный на каждом шаге (инвариант всего цикла).
6. V10 зелёный или SKIP с явной пометкой; SKIP без docker не блокирует вливание,
   но деплояторы получают пометку «стек не поднимался локально».
   Немаркированный SKIP = красный прогон (fail-closed, см. пометку в §3).
7. Откат проверен словами: для каждого S известна revert-команда в один коммит,
   legacy-пути (P1 §7) не затронуты.

## 5. Открытые вопросы (не блокируют вливание, блокируют follow-up)

- **Q1 — `CELL_*_SRC` для сборки.** Откуда берутся исходники сборки
  (локальный контекст vs внешний src): пока не зафиксировано — деплояторы
  должны подтвердить источник перед первым прод-прогоном после цикла.
- **Q2 — триггер `dev-*` не расширять.** Dev-клон работает на существующем
  триггере; добавление новых `dev-*`-веток/путей в триггеры — отдельный
  тикет, не часть P1-цикла (см. V9).
- **Q3 — DIR-семантика старых слотов.** Что считается каноном директории для
  слотов, созданных до цикла (adopt vs пересоздание, по аналогии с data-slots
  из P4 §3): решить до того, как DOCS зафиксирует контракты в S-4, иначе
  контракты зафиксируют неверную семантику.
